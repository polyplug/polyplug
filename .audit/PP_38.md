# PP-38 — Embedded Loading and Language-Parity Audit

This is the working audit ledger for Plane parent **PP-38**. Keep it until every
accepted finding is fixed, tested, documented, and closed in Plane. It is not
product documentation; product docs describe only the final current state.

## Non-negotiable direction

- Rust, C++, C#, Python, Lua, and JavaScript/QuickJS are maintained host and guest languages.
- Generally applicable features have equivalent semantics in every maintained language.
- Language mechanics live behind generators, SDKs, and loaders.
- One canonical bundle, contract, dependency, registration, lifecycle, and discovery path serves every source.
- Bundle initialization is transactional: publish the complete bundle once or publish nothing.
- Cross-compilation proves compile/link; native execution proves runtime behavior.
- Delegated findings are leads until independently verified.

## Corrective redesign — reopened 2026-07-12

**Status: REOPENED. The implementation at `9f5aca88` and follow-up commits is
architecturally non-compliant and must not be treated as the accepted design.**

The implementation introduced three redundant public ABI records:

- `InProcessBundleMetadata`
- `InProcessContractRegistration`
- `InProcessBundleRegistration`

This violates the primary requirement to reuse polyplug's existing contracts and
data model instead of creating a parallel registration schema. Passing tests and
CI only establish internal consistency; they do not make this ABI shape
acceptable.

The corrective implementation must:

1. Remove all three redundant public ABI records from Rust and every generated
   language mirror.
2. Remove the parallel in-process registration envelope from `HostApi`, all six
   host SDKs, generators, fixtures, examples, tests, and documentation.
3. Reuse the existing bundle identity/lifecycle and dependency models.
4. Represent each provided contract only with the existing `PluginDescriptor`
   and `GuestContractInterface`; generated language-owned state remains behind
   `GuestContractInterface.adapter_context`.
5. Keep complete-bundle validation and atomic publication as an internal
   staging/commit mechanism, not a second public bundle schema.
6. Preserve equivalent Rust, C++, C#, Python, Lua, and JavaScript behavior,
   runtime-local ownership, one-time ownership transfer, failure cleanup, and
   logical unload.
7. Regenerate all SDKs and current-state documentation, run the complete local
   gate and native/cross-platform CI, then replace the invalid closure evidence
   in Plane.

Do not close PP-38 again while any of the three redundant ABI records exists.
Do not solve this by renaming, merging, or wrapping those records.

## Approved in-process architecture

The feature is **in-process plugin registration**. It is not a source-loading,
artifact-loading, or native-linking mode.

Each maintained host SDK accepts plugin implementations created in its own
language:

| Host SDK | In-process implementation |
|---|---|
| Rust | Rust object/factory |
| C++ | C++ object/factory |
| C# | C# object/factory |
| Python | Python object/factory |
| Lua | Lua object/table/factory |
| JavaScript/QuickJS | JavaScript object/factory |

Generated SDK code adapts that language-native implementation to canonical
contract registrations. The owning language loader retains the object,
factories, callbacks, and runtime state. Core stages the complete bundle,
validates it, and atomically publishes it through the normal registry.

One core source API exposes equivalent path, code, bytes, and in-process
registration semantics where the source form applies. The in-process form does
not create a DLL/shared object, evaluate source text, load assembly bytes, or
materialize a temporary artifact.

### Ownership and lifecycle contract

- Registration accepts generated, typed language-SDK adapters rather than
  arbitrary object pointers.
- The loader owns every language object and ABI bridge for the resident bundle.
- Factory and implementation state is bundle-owned and runtime-local, never
  process-global.
- Core validates the full provider, dependency, metadata, and function set
  before one atomic registry commit.
- Logical unload blocks new calls, waits for active calls and leases, destroys
  instances, unregisters contracts, invalidates handles, and releases the
  loader-owned resident.
- Logical unload does not promise to unload the host language runtime or machine
  code already resident in the host process.
- Rust panics, C++ exceptions, managed exceptions, and scripting-language
  failures are translated before crossing the generated ABI boundary.
- All six host SDKs expose equivalent registration, discovery, lifecycle,
  failure, and unload behavior.

## Independently verified correctness findings

### PP-43 — Cross-language revision synchronization — critical

Status: remediated.

`HostApi.registry_revision` returns the current registry revision value after the
runtime performs its acquire load. Every maintained host caller compares that
value before direct dispatch and re-resolves after a registry mutation.

Evidence:

- `crates/polyplug/src/runtime_store.rs` — `publish`, `current_revision`
- `crates/polyplug_abi/src/host/host_api.rs` — `HostApi.registry_revision`
- `crates/polyplug_codegen/src/generators/rust.rs` — callback invocation
- `crates/polyplug_codegen/src/generators/python.rs` — ctypes callback invocation
- `crates/polyplug_codegen/src/generators/lua.rs` — Lua callback invocation
- `crates/polyplug_codegen/src/generators/js_quickjs.rs` — runtime bridge callback

### PP-44 — Transactional bundle preparation/commit — critical

Status: remediated.

Loader initialization stages every contract, dependency, provider, metadata, and
resident before publication. Core validates the complete prepared bundle and
commits one registry snapshot. Any preparation or validation failure reclaims
the staged resources without changing discovery state.

Evidence:

- `crates/polyplug/src/runtime.rs` — `load_manifest_with_source`
- `crates/polyplug/src/runtime_store.rs` — `register_guest_contract`, `declare_bundle_dependencies`
- `crates/polyplug_lua/src/loader.rs` — sequential registration and VM ownership
- `crates/polyplug_python/src/loader.rs` — sequential registration and leaked loader-data boxes

### PP-45 — Loader parity and failure cleanup — high

Status: remediated.

QuickJS consumes every generated registration. Python initialization uses
balanced context cleanup for every source form. Core requires the exact manifest
provider set and validates native function tables after loader initialization.
Multi-contract success, rollback, and unload cleanup are covered across loaders.

Evidence:

- `crates/polyplug_js/src/loader.rs` — first registration only
- `crates/polyplug_codegen/src/generators/js_quickjs.rs` — emits every plugin registration
- `crates/polyplug_python/src/lib.rs` — path versus source init-stack cleanup
- `crates/polyplug/src/runtime.rs` — post-load validation observes only registered contracts

### PP-46 — Runtime-local in-process factory state — high

Status: remediated.

Generated adapters retain factories, callbacks, interface tables, and
implementations in a resident owned by exactly one Runtime. Successful
registration transfers that resident once; rejected registration leaves it
reusable. Two-runtime, unload, failed-unload, and re-registration tests cover
all six host SDKs.

### Additional verified architecture repairs

- Logical unload removes the bundle manifest and its reload recipe.
- Runtime metadata uses the concrete loader language rather than treating every
  native-dispatch bundle as Rust.
- `BundleInitContext` path ownership matches the synchronous initialization
  lifetime used by native and .NET loaders.
- Lifecycle callback requirements are identical for loader and in-process
  registrations.
- Source-specific validation is separated from path-only artifact and signature
  rules.

These repairs are covered by PP-40 and PP-42.

## Independently verified simplification findings

Tracked by **PP-47**:

Status: remediated.

1. `RuntimeLanguageBridge` plus Lua/JS bridge implementations form a disconnected, incomplete second host-contract architecture. The generated `HostContractInterface` path is canonical.
2. Native, JS, and Lua loader config types carry no effective setting.
3. Six generators duplicate bundle-manifest emission.
4. `ManifestData.bundle_dependencies` duplicates the canonical `[[dependency]]` grammar and has no real manifest consumer.
5. `BundleLoader::loader_language` is explicitly informational and unused.
6. `LogSink` wraps one closure implementation and only forwards `emit`.
7. Loader manifests repeat default `[lib].name`/`path`; Lua/Python repeat normal dependencies under dev-dependencies; Python repeats Cargo's default integration-test target; Rust host examples duplicate workspace paths.

### Rejected cleanup claim: loader `cdylib` outputs

The loader crates do not define binary targets. Their `cdylib` outputs are
shared libraries loaded by non-Rust hosts through exported C-ABI loader factory
functions. Keep `crate-type = ["rlib", "cdylib"]`. The redundant configuration
around those factories is removable; the shared-library artifact is required.

## External research conclusions

Primary-runtime documentation was researched through the Firecrawl CLI. The
research applies to path/code/bytes loading, not to the approved in-process
object-registration feature:

- Native raw in-memory PE/ELF/Mach-O mapping is not portable and bypasses normal relocation, dependency, signing, W^X, and teardown behavior.
- Native artifact bytes should be verified and materialized privately before OS loading.
- .NET assembly bytes naturally map to `AssemblyLoadContext.LoadFromStream`.
- CPython supports source/code execution through interpreter APIs but process-wide interpreter constraints remain.
- Lua/LuaJIT and QuickJS naturally accept source or runtime-supported bytecode; bytecode compatibility must be validated by the loader/runtime version.
- Physical source-loading mechanics differ, while equivalent user-visible semantics remain required.
