  <name>Task 3: Architectural Decision - Host Contract Instance Support</name>
  <decision>Should this phase implement host contract instance support for the guest host contract caller, or defer to a later phase?</decision>
  <context>
    The guest host contract caller (guest code calling host contracts) currently does not pass HostContractInstance to dispatch calls. This violates INST-04 for host contract paths.

    Per CONTEXT.md: "this phase is purely about naming consistency" and "instance model is already implemented" (for guest contracts).

    However, the new ABI (HostContractInterface) includes create_instance/destroy_instance and get_host_contract returns HostContractInstance. The guest host contract caller needs:
    1. Store HostContractInstance (from get_host_contract)
    2. Pass instance to dispatch calls
    3. Handle singleton vs multi-instance lifecycle

    This requires architectural changes beyond naming.
  </context>
  <options>
    <option id="defer-instance">
      <name>Defer Instance Support (Recommended)</name>
      <pros>
        - Matches CONTEXT.md scope (purely naming)
        - Focus this phase on naming consistency
        - Create follow-up phase for host contract instance support
        - Less risk of introducing bugs in naming refactor
      </pros>
      <cons>
        - Generated code has TODO with interim nullptr
        - Multi-instance host contracts won work until follow-up phase
        - Singleton contracts may work (if impl ignores instance param)
      </cons>
    </option>
    <option id="implement-instance">
      <name>Implement Instance Support Now</name>
      <pros>
        - Completes INST-04 for all paths
        - Generated code fully functional
        - No interim TODO/placeholders
      </pros>
      <cons>
        - Exceeds stated phase scope
        - Increases complexity and risk
        - May introduce bugs alongside naming changes
      </cons>
    </option>
  </options>
